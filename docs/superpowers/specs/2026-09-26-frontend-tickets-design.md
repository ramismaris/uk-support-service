# Фронтенд: обращения, чат, статусы (Ф2 + Ф3 + Ф4)

Второй подпроект фронтенда. Строится на [фундаменте](2026-09-26-frontend-foundation-design.md): вход, каркас, тема, `shared/api`, `entities/session`, `entities/user` уже есть.

Контекст: [product.md](../../product.md) (панель менеджера), [ticket-lifecycle.md](../../ticket-lifecycle.md), [architecture.md](../../architecture.md#контракт-api) (кнопка «Открыть», чат, смена статуса, события WebSocket).

## Цель и критерии готовности

Менеджер в панели проходит демо-сценарий целиком:

- видит список активных обращений с непрочитанным и срочностью, фильтрует по статусу и «мои»;
- открывает обращение — из списка или кнопкой «Открыть» в уведомлении Max;
- читает переписку и детали, отвечает текстом и файлами;
- берёт в работу, просит ответ клиента, закрывает, отклоняет с причиной;
- всё, что делают клиент и другие сотрудники, появляется без перезагрузки.

Технически: `frontend/scripts/check.sh` зелёный; ручная проверка по чек-листу (раздел «Проверка») на настоящем бэкенде.

## Вне рамок

- Фильтры по дому и категории: в API нет справочников. Просим бэкенд `GET /staff/buildings` и `GET /staff/categories`; фильтры — отдельной задачей после них.
- Вкладка «Отфильтровано» и ML-метки (Ф6), архив (Ф9), контент и пользователи (Ф5), бренд из темы (Ф11).

## Роуты и раскладка

```
/staff                 список; на ≥lg справа — «Выберите обращение»
/staff/tickets/:id     обращение
```

| Ширина | Раскладка |
|---|---|
| < `lg` (телефон, Max) | по одному экрану: список → обращение. У обращения — «Назад» и вкладки «Чат» / «Детали» |
| `lg` … < `xl` | список \| чат; детали — выезжающая справа панель по кнопке в шапке обращения |
| ≥ `xl` | список \| чат \| детали |

Сайдбар навигации app-shell остаётся на ≥lg. Список на ≥lg не перемонтируется при переходе между обращениями (общий layout-роут).

Фильтры — в query-параметрах URL (`?status=NEW&mine=1`): переживают перезагрузку, попадают в ссылку и сохраняются при переходе список ↔ обращение.

### Кнопка «Открыть» из Max

При запуске в Max `start_param` вида `ticket_<id>` → после входа один раз открывается `/staff/tickets/<id>`. Разбор — чистая функция `ticketPathFromStartParam(param: string | null): string | null` (только `ticket_` + положительное целое; остальное → `null`). Переход выполняет `RoleRedirect` для сотрудника: если путь из `start_param` есть и ещё не использован в этой сессии страницы — ведёт туда, иначе на `/staff`.

## Структура FSD

Правило проекта: код одного потребителя живёт в нём; в `features`/`widgets`/`entities` выносим со вторым потребителем.

| Слайс / сегмент | Что |
|---|---|
| `entities/ticket` | типы (`TicketListItem`, `TicketDetail`, `TicketStatus`, `TicketFilters`), подписи и тона статусов, ключи кэша `ticketKeys`, запросы `useTicketList(filters)` (infinite), `useTicket(id)`, функции для реалтайма `invalidateTicketLists`, `invalidateTicket`; UI: `TicketStatusBadge`, `UrgentMark` |
| `entities/message` | тип `Message`, ключи `messageKeys`, `useMessages(ticketId)`, `appendMessage(queryClient, message)` (без дублей по `id`); UI: `MessageBubble` с вложениями |
| `pages/tickets` | layout-роут и оба экрана: список с фильтрами и «Показать ещё», экран обращения, чат, поле ввода с файлами, детали, кнопки статусов, диалог отклонения, отметка «прочитано» |
| `shared/lib/ws` | `createReconnectingSocket`: подключение, переподключение с задержкой, обработка кодов закрытия; без знаний о домене |
| `shared/ui/lottie` | `LottieAnimation` (ленивый плеер, reduced motion → статичный кадр) и файлы анимаций |
| `shared/config` | + `ticketPath(id)`, `routePaths.ticket = '/staff/tickets/:id'` |
| `app/realtime` | подключает WebSocket, когда вошёл сотрудник; раскладывает события по кэшам через функции `entities` |

## Данные

### Список

- `useInfiniteQuery` поверх `GET /api/v1/staff/tickets`, страницы по 50 (`skip`/`limit`), следующая страница — пока загружено < `total`.
- Фильтры → параметры API: `status` (`NEW` | `IN_PROGRESS` | `WAITING_CLIENT` | нет), `mine` (`true` | нет). Чистые функции `parseTicketFilters(URLSearchParams)` и `ticketFiltersToSearch(filters)` — туда и обратно, неизвестные значения отбрасываются.
- Строка списка: номер, тип (заявка / вопрос), категория, адрес (`building.address`, кв.), начало описания, имя клиента, бейдж статуса, иконка срочности (`Siren`) для `URGENT`, точка непрочитанного (`unread`), время создания (относительное: «5 мин», «вчера», дата).
- Внизу — «Показать ещё» и «N из total».
- Пусто → Lottie «Обращений нет»; с фильтром — «По фильтру ничего не найдено» + «Сбросить фильтры».

### Обращение

- `GET /api/v1/staff/tickets/{id}` → детали; `GET …/messages` → чат.
- 404 → экран «Обращение не найдено» со ссылкой на список.

### Реалтайм

`GET /api/v1/ws?token=<token>` (через прокси Vite, `ws: true`). События — [architecture.md](../../architecture.md#контракт-api).

| Событие | Действие |
|---|---|
| `message_created` | `appendMessage` в кэш чата `message.ticket_id`, если кэш есть; дубль по `id` игнорируется |
| `ticket_created` | инвалидировать все списки |
| `ticket_updated` | инвалидировать все списки и карточку `ticket.id` |
| переподключение | инвалидировать списки, все карточки и чаты |

Событие `ticket_updated` несёт строку списка, а не карточку (нет истории и `allowed_statuses`), и приходит в том числе при смене статуса — поэтому карточку перезапрашиваем, а не собираем из события. Решение, что инвалидировать, — чистая функция `planRealtimeUpdate(event)` → список действий; её тестируем.

Сокет:

- открывается, когда есть токен и пользователь — сотрудник; закрывается при выходе;
- обрыв → переподключение с задержкой 1, 2, 4, 8, 16, 30, 30… с (чистая функция `reconnectDelay(attempt)`); успешное подключение сбрасывает счётчик;
- код `4401` → сессия сбрасывается, как при 401 (токен и кэш); `4403` → не переподключаемся;
- пока соединения нет — в шапке списка индикатор «Нет связи» (иконка `WifiOff`).

### Непрочитанное

`POST …/read` отправляется, когда чат виден: при открытии обращения (на телефоне — при показе вкладки «Чат») и при приходе сообщения клиента в открытый чат. Не чаще одного запроса в секунду на обращение.

## Чат

- Порядок — по времени, прокрутка к последнему сообщению при открытии и при новом сообщении (если пользователь уже внизу).
- `CLIENT` — слева; `STAFF` — справа, с именем автора; `SYSTEM` — по центру, приглушённо.
- Вложения: `image/*` — превью (`<img src={file.url}>`), клик открывает оригинал в новой вкладке; остальное — ссылка с иконкой `FileText`, именем и размером.
- Новые сообщения появляются с анимацией framer-motion.
- Пустой чат → Lottie «Сообщений пока нет».

### Поле ввода

- Текст до 3000 символов; Enter — отправить, Shift+Enter — перенос строки.
- Скрепка (`Paperclip`) → выбор файлов; до 10 изображений **или** один документ, каждый до 20 МБ. Чистая функция `validateAttachments(files)` → ошибка или ок (сообщения на русском). Превью выбранных файлов с удалением.
- Отправка (`SendHorizontal`) активна, если есть непустой (после обрезки пробелов) текст или файлы.
- `POST …/messages` (`multipart/form-data`: `text`, повторяющееся `files`). Пока идёт — поле заблокировано. Успех → поле очищается, сообщение дописывается в кэш из ответа, короткая Lottie «Отправлено» у кнопки. Ошибка (в т.ч. 502 — Max не принял) → текст ошибки под полем, введённое сохраняется.
- Обращение в `CLOSED` / `REJECTED` → поле заменено строкой «Обращение закрыто — писать в него нельзя» (бэкенд отвечает 409).
- Ответ в `NEW` сам переводит обращение в работу — это делает бэкенд; фронт узнаёт из `ticket_updated`.

## Детали и статусы

Детали: клиент (имя, телефон — ссылкой `tel:`), адрес, категория, тип, описание, желаемое время, фото заявки, кто ведёт, история статусов (из → в, кто, когда, комментарий), оценка (1–5, иконки `Star`) — если есть.

Кнопки статусов строятся строго по `allowed_statuses`; таблицу переходов фронт не повторяет. Подпись по текущему и целевому статусу — чистая функция `statusActionLabel(from, to)`:

| Переход | Кнопка |
|---|---|
| `NEW` → `IN_PROGRESS` | Взять в работу |
| `IN_PROGRESS` → `WAITING_CLIENT` | Нужен ответ клиента |
| → `CLOSED` | Закрыть |
| → `REJECTED` | Отклонить |
| `CLOSED` / `REJECTED` → `IN_PROGRESS` | Переоткрыть |
| прочее → `IN_PROGRESS` | Вернуть в работу |

- `POST …/status` `{status, comment}` → ответ (карточка) кладётся в кэш, списки инвалидируются.
- «Отклонить» → диалог с обязательной причиной (непустая после обрезки, до 3000), подпись «Причину увидит клиент».
- Переход в `CLOSED` → Lottie «Обращение закрыто» один раз поверх деталей.
- Ошибка (409 — обращение уже изменили, 400) → сообщение бэкенда, карточка перечитывается.

## Иконки и анимации

- Иконки — только `lucide-react` (размер 16/20, `strokeWidth` 2). Основные: `Siren`, `Paperclip`, `SendHorizontal`, `ChevronLeft`, `PanelRight`, `FileText`, `Star`, `WifiOff`, `X`.
- Lottie (`shared/ui/lottie`): пустой список, «Выберите обращение», пустой чат, «Отправлено», «Обращение закрыто». Анимации — с LottieFiles под бесплатной лицензией (Lottie Simple License). **До вставки подбор показывается пользователю на согласование**; до этого — статичные заглушки (иконка + текст).
- `prefers-reduced-motion` → Lottie показывает первый кадр, framer-motion — через уже настроенный `MotionConfig reducedMotion="user"`.

## Ошибки

| Где | Что видит пользователь |
|---|---|
| список, карточка | текст бэкенда (или «Нет связи с сервером…») + «Повторить» |
| карточка 404 | «Обращение не найдено» + «К списку» |
| отправка сообщения | текст под полем, введённое сохраняется |
| смена статуса | сообщение бэкенда, карточка перечитывается |
| WebSocket | индикатор «Нет связи», переподключение; 4401 — выход на логин; 4403 — без переподключения |

## Инфраструктура

- `vite.config.ts`: прокси `/api` с `ws: true`; `server.host: '127.0.0.1'` — на этой машине `localhost` резолвится в `::1`, и браузер не находил dev-сервер.

## Тесты

Vitest, чистая логика:

- `ticketPathFromStartParam` — корректные и мусорные значения;
- `parseTicketFilters` / `ticketFiltersToSearch` — туда и обратно, неизвестные значения;
- `planRealtimeUpdate` — действия на каждое событие и на переподключение;
- `appendMessage` — добавление, дубль, нет кэша;
- `reconnectDelay` и решение по коду закрытия (`shouldReconnect(code)`);
- `validateAttachments` — лимиты количества, смешение фото и документов, размер;
- `statusActionLabel` — все строки таблицы;
- валидация причины отклонения;
- относительное время в списке.

UI-тестов нет.

## Проверка (ручная)

Бэкенд с демо-данными, dev-вход. Второе окно — сообщения от клиента через бота или Swagger.

1. Список: демо-обращения, срочные с иконкой, непрочитанные с точкой; фильтры меняют URL и список; перезагрузка сохраняет фильтр.
2. Телефонная ширина: список → обращение → «Назад»; вкладки «Чат» / «Детали».
3. `lg`: список | чат, детали — выезжающей панелью; `xl`: три колонки.
4. Открытие обращения снимает точку непрочитанного (и в другом окне панели).
5. Ответ текстом и фото уходит, появляется в чате; из `NEW` обращение переходит в «В работе».
6. Сообщение клиента появляется в открытом чате и в списке без перезагрузки.
7. Взять → нужен ответ → закрыть; отклонить с причиной; у админа — переоткрыть. Кнопки соответствуют `allowed_statuses`.
8. В закрытое обращение писать нельзя.
9. Остановка бэкенда → «Нет связи»; запуск → переподключение, данные перечитаны.
10. `/staff/tickets/999999` → «Обращение не найдено».
11. Тёмная тема и reduced motion.
